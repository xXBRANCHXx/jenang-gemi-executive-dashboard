# Approved broad dashboard reader

Implemented four typed tools alongside three existing narrow reporting tools: jg_list_tables, jg_describe_table, jg_query_table, jg_annualize_sales. Discovery includes 58 reviewed physical business views plus catalog, sales_lines and sales_orders (61). The source evidence contains 103 physical names; technical/auth/PII/raw proof stores are intentionally not queryable. Physical availability is checked at query time; source DDL does not prove production existence.

The approved families are catalog/sales, stock/purchasing, accounting/wallets, partners, ads/analytics, customer aggregates and website content. Typed static projections exclude customer contacts/identities, credentials, free-text notes, receipt/proof files and raw payloads. Customer activity exposes aggregate event counts only. Ads tables currently cover stored campaign settings/budgets/events, not a new external campaign-performance fetch. Website authored draft text is readable; no publication tool exists.

No caller SQL/joins/filesystem paths are accepted. Query inputs are allowlisted columns, typed bound filters, grouping and sum/count/distinct/min/max/avg metrics, ordering, limit1–200 and offset0–100000. Native grouping happens before pagination; pages can change between calls. Supported UTC datetime fields have explicit Jakarta day/month dimensions. Semantic product dimensions use saved catalog identities with snapshot provenance; size filters require both volume and unit. Native settings resolve inside PHP without copying credentials, schema boots or sync. Connections use native prepared statements, multi-statements disabled, repeatable-read read-only transactions and rollback. Application DB principal remains broad underneath; this is the previously approved application-boundary tradeoff, not new SQL access.

Scope `jg:dashboard:read` is bound to newly consented token records and privately enabled family flags. Original `jg:sales:read` tokens retain their original three data capabilities and ZERO scope. Once privately approved, all7 tool descriptors are discoverable; broader calls return a documented insufficient_scope consent challenge before any data access. Known two-scope unions are accepted only through fresh owner consent, never by upgrading refresh tokens. Per-tool securitySchemes appear at the top level and mirrored under _meta for compatibility. The new metadata scope is absent until private configuration approves every family. No live token is generated by fixture checks; normal owner OAuth consent remains required.

Financial metrics:
- sales_orders.seller_revenue records order seller/merchandise revenue once: marketplace MAX(order_net_revenue) unless zero, then SUM(recorded line revenue); paid website net_revenue; direct merchandise_total excluding shipping; partner stored revenue_total with recorded item fallback. Direct/partner unpaid receivables are included, so this is not cash.
- sales_lines.line_revenue is recorded line revenue. It is distinct from whole-order revenue; no guessed allocations of order totals to filtered products. Marketplace gifts contribute no units. Status/deletion rules follow extracted dashboard paths.
- Summing repeated physical marketplace order_net_revenue is rejected.
- All four semantic sources must succeed for a complete stored-source total. Available-source results are returned as observed_partial_subtotal when a source is unavailable; missing sources are never zero. Full annualization is blocked with null projection and error status, while preserving the observed monetary subtotal and sanitized source diagnostics. The capped native scans fail if exceeded, never silently aggregate a prefix.
- Upstream synchronization and cross-channel duplicate/consolidation reconciliation remain unverified. Returned consolidated stored channel records are not certified all-business revenue or profit. No source refresh is performed.
- Annualization is a monetary run rate over explicit completed-day or elapsed-time cutoff, with exact observed decimal IDR values and calendar-year seconds. October1 completed_days returns insufficient history, not zero. Current-day elapsed-time projections are volatile, not forecasts or actual annual revenue.

Official contract: https://developers.openai.com/plugins/build/auth . Real client consent behavior still requires cloud verification.

When privately approved, jg_get_context also requires the dashboard scope and returns the same standard consent challenge for a narrow token. With broad approval disabled it keeps its original narrow behavior; existing product-count calls remain unchanged. A newly consented broad/combined token gets normal context without another challenge. Actual client handling remains a cloud verification gate.

Partner binding parity: reader matches the existing application's exact local.server to localhost hostname alias, only for partner connections, preserving DB name/user/credentials. Read-only setup runs after connection; failure never retries without it. Diagnoses expose only enum reasons/SQLSTATE/driver codes and binding labels, never raw DB error messages, DSNs or credentials. No env/settings/grants/schema mutation. Native production failure cause remains an actual cloud diagnostic gate.

Partner date basis (MCP0.2.4): `partner_date_basis` is an optional enum on jg_product_report, jg_query_table semantic sales_lines/sales_orders, and jg_annualize_sales. `order_time` remains the default and uses COALESCE(order_timestamp,created_at) assumed UTC; historical local-input timezone is unverified and explicitly warned. `recorded_at` uses created_atUTC in both fixed SELECT bounds and Jakarta grouping. It does not repair timestamps, change other channels or reinterpret physical table fields. Record-time reports count backdated orders when entered. Physical views reject the option. Product reports still honor the original narrow brand/account/partner grant. Results expose selection and all-source date provenance. No schema migration, permission change or business-record mutation is required.
